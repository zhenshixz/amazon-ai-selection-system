## 一、产品定位与实施原则

当前交付物是一个可以由用户实际输入关键词、选择锚点、执行真实分析并查看报告的可操作原型。当前先用它验证业务流程和报告结构；运营确认整体方向后，再围绕已经验证的页面补充逐页流程与需求说明，最后交给技术团队排期正式开发。

因此第一版采用以下原则：

1. **流程真实性优先**：核心数据必须来自 Amazon 公开页面或已授权 MCP，不使用演示数字填充。
2. **允许轻量实现**：可以直接在现有 Next.js 服务端调用单一 MCP、使用内存缓存和简单字段映射，不提前建设数据库、任务队列或多租户平台。
3. **结论可追溯**：每个数字和建议都能追溯到商品、关键词、来源、指标周期与采集时间。
4. **控制复杂度**：第一版不做复杂评分、全属性组合、自动成功率预测或多数据源融合。
5. **允许人工校正关键中间结果**：英文候选词在调用前可编辑，减少术语错误和无关场景误入分析。
6. **原型不等于最终架构**：当前轻量接口和数据结构用于验证业务需求，不要求直接成为正式系统最终架构；正式技术方案在阶段 3 由技术团队结合需求评估。

## 二、当前系统基线

当前系统已经具备：

- 用户输入 Amazon US 关键词并读取第 1 页商品。
- 用户收藏锚点商品并提取 Listing 公开详情。
- 读取搜索结果前 1-3 页，记录原始数量、重复 ASIN 和去重样本。
- 执行真实后端分析阶段，生成设计属性统计、商品明细、机会结论和改款参考方案。
- 使用 Amazon 商品图作为竞品参考图，不冒充 AI 生图。

当前仍缺少：

- 设计属性对应的真实关键词搜索量、趋势和竞争度。
- “设计共性 -> 搜索需求 -> 空白机会 -> 改款依据”的完整证据链。
- 评论正文及基于评论正文的真实痛点聚类。
- 对复杂设计表达和同义词的稳定语义归一化。
- 可以约束数字、引用证据的大模型解释层。

## 四、GitHub 项目的使用方式

研究项目：`liangdabiao/amazon-sorftime-research-MCP-skill`

### 可直接借鉴

- 市场扫描、关键词验证、竞品验真、评论痛点和改款建议的分析顺序。
- SIF、西柚和卖家精灵的工具用途说明与常见字段陷阱。
- 报告必须记录筛选口径、样本范围、原始数据、置信度和缺失项的质量检查思想。
- “已确认事实 / 假设 / 缺失数据 / 下一步验证”分层输出方式。

### 禁止直接使用

- 仓库内 `_mock_*` 生成的模拟搜索量、竞争度、趋势和商品数据。
- 针对特定 ASIN、品类或报告写死的结论和推荐文案。
- 未经验证的固定评分阈值和所谓成功率。
- 公共仓库 `.mcp.json` 中的任何凭证或密钥。
- 为了复用脚本而在当前原型额外引入常驻 Python 服务。

### 原型落地决策

GitHub 项目作为“分析方法和字段参考库”，不是运行时依赖，也不是新的数据供应商。原型在现有 Next.js 后端中实现最小真实调用，避免把 Claude Skills、Python 报告脚本和当前页面形成两套运行流程。

## 五、目标业务流程

```text
用户输入基础关键词
  -> Amazon 第 1 页选择锚点
  -> 提取锚点 Listing 与设计属性
  -> Amazon 前 1-3 页采集并按 ASIN 去重
  -> 统计设计共性和代表竞品
  -> 生成 3-8 个可编辑英文候选词
  -> MCP 获取真实搜索需求与竞争指标
  -> 展示关键词证据表和需求/竞争四象限
  -> 形成有限组合的空白机会假设
  -> 生成有证据引用的改款方案与风险
  -> 输出最终报告
```

## 六、第一版 P0 需求

### P0-1 英文候选词生成与确认

输入：用户基础关键词、人群/性别、锚点设计属性、市场高频设计属性。

规则：

- 优先使用可维护的标准属性词典，例如“宽松版型 -> baggy / relaxed fit”“阔腿 -> wide leg”。
- 生成“单一设计属性 + 基础品类词”和少量“双设计属性 + 基础品类词”。
- 每次最多 10 个词，每个组合最多两个设计变量；同一需求至少生成“人群前置”和“for men/for women”两类常见表达。
- 每个候选词保存需求组、设计词根、人群和品类要素；只有同时满足必要要素的表达才能进入对应需求组。
- 场景词必须有 Listing 原文证据；无证据时不能默认加入旅行、度假、通勤等词。
- 候选词必须在调用 MCP 前展示，允许修改、删除和取消勾选。
- 未知或低置信度属性不自动翻译，显示“需要确认”。

### P0-2 西柚 MCP 真实调用

- 默认站点为 US，与当前 Amazon 数据保持一致。
- 第一版只自动调用 `get_keyword_info`，一次传入全部候选词。
- 保存周搜索量、ABA 报告排名、竞争难度、点击转化率、自然位滚动率、CPC、头部 ASIN 点击份额和转化份额。
- 保存数据源、国家、指标周期、采集时间和原始关键词。
- MCP Secret 只从服务端环境变量读取，不进入前端、Git 或报告。
- 相同站点和关键词使用短期进程内缓存，避免一次演示中重复扣减额度；持久缓存及缓存周期必须在正式实现前再确认供应商授权条款。

### P0-3 简单透明的机会比较

- 不生成黑盒综合分或成功概率。
- 先展示需求组汇总，再保留每个关键词的原始指标供追溯。
- 同组关键词去重后汇总周搜索量；竞争难度、CPC 和转化率按各词周搜索量加权，不能直接相加。
- 使用本次需求组的搜索量中位数和加权竞争中位数形成相对判断，只用于组间比较。
- “高需求、低竞争”统一表述为“优先验证方向”，不能直接称为蓝海或确定机会。
- 搜索量低、竞争高、头部点击集中或 CPC 高时分别显示对应风险，不混成一个无法解释的分数。
- MCP 未返回的字段保持空值并显示原因。

### P0-4 报告信息结构调整

在报告质量摘要之后、“选品建议与差异化机会”之前新增：

1. **设计特征关键词映射**：中文设计属性、必要要素、不同搜索表达、生成依据和人工确认状态。
2. **同义搜索需求汇总**：覆盖词、有效词数、合计搜索量、加权竞争、加权 CPC、主要流量词和口径说明。
3. **关键词需求证据表**：保留每个完整搜索词的搜索量、ABA、竞争难度、CPC、转化率、周期和来源。
4. **机会与风险摘要**：只归纳已返回指标，不补充外部数字。

报告后续顺序保持：产品明细 -> 机会结论 -> 锚点总览 -> 改款方案 -> 改款依据 -> 最终策略。

### P0-5 改款方案证据约束

第一版中，凡匹配到已验证候选词的改款方案必须包含：

- 锚点原始设计属性及原文证据。
- 目标设计属性和对应英文候选词。
- 关键词搜索量、竞争难度和数据时间。
- 一个真实竞品 ASIN 或明确标记“缺少竞品证据”。
- 为什么值得验证、主要风险、下一步验证动作。
- 数据置信度与仍缺失的信息。

未匹配到候选词的方案允许保留 Listing 参考，但必须显示“关键词数据待验证”；本轮至少跑通一个从设计属性到真实 MCP 指标的完整方案。

禁止内容：

- 没有关键词数据却声称“高需求低竞争”。
- 把 Amazon 评论数当作关键词搜索量。
- 把方案称为“成功率高”或承诺确定销量。
- 为了填满九个方案而输出重复、无证据或无业务差异的方案。

### P0-6 失败降级和内部访问

- MCP 缺少密钥、超时、额度用完或返回空数据时，保留 Amazon 分析结果并明确显示失败原因。
- 不使用默认样例数据进行降级。
- 允许用户修改候选词后只重试关键词验证阶段，不重新采集前三页商品。
- cpolar 公网入口启用 MCP 前增加最小应用访问控制、接口频率限制和单次关键词数量限制。
- 页面不得展示或返回 MCP Secret。

## 七、P1 与 P2 范围

### P1：证据增强

- 对前 1-2 个候选机会词人工触发西柚 ABA 趋势或竞争 ASIN 深度查询。
- 使用 SIF 对少量候选词执行第二来源验证，比较搜索需求、竞争和机会结论的一致性。
- 增加一次受约束的大模型调用，完成英文术语校验、证据归纳、方案去重和改款理由生成。
- 建立按品类版本化的服装设计属性 Schema，提高裤装、Polo、T 恤等类目的提取覆盖率。

### P2：正式系统候选能力

- 评论正文采集及面料、尺码、做工、色差、舒适度等痛点聚类。
- 销量、BSR、关键词和价格的 30/90/180 天趋势。
- 退货原因、FBA 费用、采购成本、头程和利润测算。
- 多数据源质量对比、自动切换、持久缓存、任务队列、账号和权限体系。
- 根据正式授权和调用成本重新选择长期数据供应商。

## 八、大模型使用边界

第一版数据抓取、数值计算和 MCP 工具选择不交给大模型。需要接入大模型时，只传入精简结构化数据：

- 基础关键词、站点和目标人群。
- 锚点及代表竞品的标准设计属性和原文证据。
- 3-8 个候选词及 MCP 返回指标。
- 产品约束和待解决业务问题。

大模型只负责：

- 检查英文术语是否自然且符合 Amazon 搜索表达。
- 解释设计属性与关键词需求、竞争之间的关系。
- 合并重复方向，形成改款理由、风险和下一步验证动作。
- 输出严格结构化结果，并引用商品 ASIN 和关键词 ID。

大模型不得：

- 修改、推算或补齐 MCP 原始数值。
- 使用没有输入证据的旅行、度假等默认场景。
- 把低频供给直接解释为真实需求空白。
- 输出无法追溯依据的成功率、销量预测或利润结论。

## 九、原型数据口径

原型至少区分以下字段：

| 字段 | 含义 | 来源 |
|---|---|---|
| `amazonDemandProxy` | Amazon 公开月购买提示；缺失时可单独展示评论数，但二者不能混称销量 | Amazon 页面 |
| `amazonCompetitionProxy` | 评论门槛、Sponsored 和市场样本形成的页面代理信号 | 本地规则 |
| `keywordWeeklySearchVolume` | 关键词周搜索量 | MCP |
| `keywordCompetitionDifficulty` | 供应商返回的关键词竞争难度 | MCP |
| `keywordCpc` | 建议竞价或 CPC | MCP |
| `keywordTopAsinShare` | 头部 ASIN 点击/转化份额 | MCP |
| `keywordEvidenceSource` | 数据提供方、站点、周期和采集时间 | MCP 元数据 |

上述字段禁止合并成一个未标注来源的“市场热度”或“竞争度”。

## 十一、第一版验收标准

- 用户不导入 CSV，仅输入基础关键词即可完成 Amazon 搜索、锚点选择和关键词真实验证。
- 系统自动生成 3-8 个候选词，用户可以在调用前修正。
- 一次分析的默认 MCP 自动调用只有 `get_keyword_info` 一次。
- 页面所有搜索量、竞争难度、CPC 和集中度都能看到来源、周期和时间。
- 至少一个改款方案能够完整展示“设计证据 -> 英文关键词 -> MCP 指标 -> 机会判断 -> 改款动作”。
- MCP 失败或无数据时不出现任何模拟数值，现有 Amazon 流程仍可继续完成。
- 旅行等场景没有 Listing 证据时不会进入候选词或最终方案。
- 同一方向不会为了凑数量生成多张重复方案。
- MCP Secret 不出现在客户端和版本库中，公网入口不能被匿名无限调用。

## 十二、待确认与账号准备

进入实现前需要确认：

1. 第一数据源是否按当前建议确定为西柚洞察。
2. 西柚账号控制台实际取得的 MCP 接入凭证和当前可用额度。
3. SIF 是否已有公司账号和可用 MCP Secret，以便后续执行少量对照测试。
4. 内部演示入口采用哪一种最小访问方式。

不需要提供平台账号密码。由账号持有人登录平台生成 MCP Secret，再将 Secret 写入本机项目的 `.env.local`；文档和代码只记录环境变量名称，不记录真实值。

## 十四、2026-09-08 产品与技术调整方案（提案，待统一实施）

本节对应 ISSUE-014～016，补充可开发的解决方案，不代表已完成实现；完整逐页技术文档仍暂停。西柚已接入，前文账号准备属于历史阶段，当前不再要求重复提供西柚凭证。

### 1. 产品流程及页面职责

| 环节 | 产品调整 | 技术处理与输出 |
|---|---|---|
| 锚点特征拆解 | 按品类展示袖长、袖型、领型、版型、面料、结构、图案、功能；每项可展开商品原文，可纠正，未识别留空 | 合并 ASIN 时保留详情；统一特征注册表，输出 featureId、dimension、标准值、原词、ASIN、来源字段及原文引用；用户修正单独保存 |
| 需求方向确认 | 展示所有已识别特征及英文词根，区分已选择、预算暂缓、缺少映射；建议默认选择 6–8 个方向，可调整 | 优先锚点证据与维度覆盖，避免前三高频独占；性别/品类/特征组成需求组；建议单轮最多 20 个查询表达，前后端一致校验 |

### 2. 规则、数据源和大模型的职责

- 代码负责：ASIN 合并、维度与别名归一、候选覆盖/预算、指标计算、周期一致性、来源追溯、互斥校验及结果状态。
- 西柚负责：返回所查询表达的真实需求与竞争指标。当前 get_keyword_info 不等于关键词扩展，不能承诺全市场召回；反查/扩词需另行核对工具字段及额度后再接。
- 大模型负责：规则无法覆盖的文本特征建议、证据约束下的具体改动与商业解释。首轮建议优先用于方案生成，避免每件商品都发起独立调用。
- 不允许模型生成搜索量、销量、成本、成功率、未经证实的面料参数或评论痛点。提取结果必须引用存在的原文；语义是否成立仍需抽样人工验收。
- 规则适合稳定常见词，新增特征可以由模型提出待确认映射，审核后入词典；避免固定词典永远漏掉新设计，也避免模型自动污染词典。

### 3. 轻量可实现的方案生成机制

1. 为每个锚点建立已知属性集；将袖长与袖型拆开，将 unknown 与不存在分开。
2. 选择有商品依据、且需求验证结果可用的设计方向；数据不足的方向可保留为探索假设，并写明缺口。
3. 形成证据包：锚点属性、参考竞品与原文、需求组及原始指标、可用评论引用（没有则不传）、缺失字段。
4. 一次生成最多 3 个结构化方案，每个默认修改 1–2 个属性，输出 anchorAsin、keepFeatures、changes、resultingFeatures、evidenceIds、rationale、unverifiedClaims、nextValidation。
5. 代码检查锚点/引用 ID 存在、改前状态与已知属性一致、同维度无互斥冲突、需求组能对应改动；按锚点和标准化改动组合去重。校验失败允许一次修正，仍失败则保留证据并提示方案未生成。
6. 单个特征词的指标仅支持该特征方向。只有查询到对应组合表达且要素匹配，才能显示“组合需求已查询”；这仍不证明供给空白或成功率。
7. 暂不建立综合机会分、自动成功率或复杂组合穷举。相对需求/竞争只作本批比较；工艺和成本缺乏数据时标为待核验。

### 4. 最小数据与接口边界

- FeatureEvidence：特征、维度、标准值、ASIN、原文字段/引用、提取方式、用户确认状态。
- DemandGroup：人群/品类/特征必要要素、候选表达、查询状态、原始证据 ID、汇总指标、周期与覆盖说明。
- Proposal：锚点、保留项、改动前后、改后属性组合、引用 ID、依据及未验证项、状态、版本。
- 当前 Next.js 前后端可继续使用，无需本轮拆微服务；数据源与模型调用放服务端，密钥不下发浏览器。模型提供商和访问方式尚待配置确认。
- 关键词步骤保留现有接口并调整预算/分组校验；方案生成独立为服务端步骤，允许仅重试方案生成，不重新采集 Amazon 或重复查询 MCP。
- DEMO 先保持现有任务方式；正式开发再补持久化项目/任务/证据快照，长任务保存状态与幂等标识，保障刷新恢复和避免重复扣费，无需先上复杂队列集群。
- 用户更改锚点特征后使受影响候选组及方案过期；修改候选词仅使相应验证及下游方案过期；图像引用方案版本，不能沿用旧方案图冒充新结果。

### 5. 验收与实施顺序

第一轮优先特征证据链和具体文字方案；第二轮在运营确认文字有价值后决定生图。

- 用运营这批衬衫样例验证泡泡袖、荷叶边、宽松进入候选池；另用裤装验证维度与品类不串用。
- 抽查同 ASIN 详情不被覆盖，所有已识别标签都有候选/暂缓/待映射状态。
- 手工复算一个需求组，验证同词去重、周期、搜索量合计、加权指标及缺失值处理；“无数据”不得展示为 0 需求。
- 抽查每个方案能定位锚点与原文，能说清具体改动；袖长不被误当袖型替换，未知属性不虚构为改前事实。
- 覆盖 MCP 无结果、超时、模型引用错误三种降级情况；数字保持真实，失败步骤可独立重试。
- 生图如纳入另行验收：图文一致、未要求部位保留、图像来源与概念图标识清晰；不以视觉好看替代需求验证。
