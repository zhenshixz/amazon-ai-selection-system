## ISSUE-001：Listing 详情字段不完整且状态表达不准确

**状态：已完成**  
**优先级：高**

### 现象

- 颜色数量显示 `--`。
- 设计特征出现“设计属性待提取”“来源：Amazon Listing”等兜底标签。
- 部分字段为空时，状态仍显示“已提取”。

### 当前原因判断

1. Amazon 公开详情页并不稳定返回颜色变体、BSR、上架日期、材质等字段。
2. Amazon 返回验证页、精简页面或备用读取页面时，可能只有标题而没有完整详情模块。
3. 当前设计属性规则主要依赖标题和 Bullet 文本，覆盖范围有限。
4. 现有状态只表示请求成功，没有区分完整提取和部分提取。
5. “来源：Amazon Listing”属于数据来源说明，不应该显示为设计属性。

### 处理方向

- 将状态拆分为：`完整提取`、`部分提取`、`提取失败`。
- 为颜色、材质、领口、袖型、图案、BSR、上架日期分别记录字段状态和来源。
- 联合解析标题、Bullet、详情表、变体节点及页面内可用结构化数据。
- 扩充服装设计属性词典，并对同义词做归一化。
- 删除“设计属性待提取”和“来源：Amazon Listing”这类伪属性标签。
- Amazon 确实没有公开的数据统一显示“Amazon 未公开”。

### 验收标准

- 页面状态与实际字段完整度一致。
- 数据来源不再混入设计属性。
- 没有识别结果时显示明确原因，不显示虚假属性。
- 任意单个字段缺失不会影响其他已取得字段的展示。

### 完成记录（2026-09-01）

- Listing 解析新增颜色、BSR、上架日期、设计属性、字段完整度和来源，并在直连数据不完整时合并备用通道结果。
- 页面按真实完整度显示“完整提取 / 部分提取 / 提取失败”，未取得字段统一显示“Amazon 未公开”。
- 数据来源和兜底文案不再混入设计属性。真实验收样本显示“部分提取 50%”，同时保留已取得的 BSR 和版型字段。

## ISSUE-002：竞品搜索中间页偶发解析失败

**状态：已完成**  
**优先级：最高**

### 现象

- 同一个关键词采集前三页时，第 1 页和第 3 页成功，第 2 页出现：
  `Amazon page loaded, but no products could be parsed.`
- 系统仍允许使用两页样本继续进入分析。

### 当前原因判断

1. Amazon 可能返回 HTTP `200`，但正文实际是验证页、异常模板、空结果模板或发生了页面结构变化。
2. 当前备用数据通道只在 HTTP 失败或命中特定验证码文本时触发。
3. 页面返回成功但解析结果为 0 时，没有自动切换备用来源重新解析。
4. 单页任务缺少独立重试入口，分析按钮也没有明确提示当前仅使用了部分页面。

### 处理方向

- 将“请求成功”与“解析成功”合并为完整校验链路：必须识别到有效 ASIN 和商品列表才算成功。
- 解析结果为 0 时，自动切换备用读取通道并重新解析。
- 每页增加有限次数重试、退避间隔和不同请求标识，避免重复命中同一异常响应。
- 校验分页参数和实际返回页码，避免第 2 页错误返回第 1 页或空模板。
- 在界面增加“重试本页”和“重试失败页”操作。
- 默认要求三页全部成功后再生成完整报告；确需继续时明确标注“部分样本报告”。

### 验收标准

- 连续多次使用不同关键词采集时，三页均能取得有效商品，或给出可操作的最终失败原因。
- 任一页首次解析为 0 时会自动执行备用通道，不直接结束任务。
- 页面级失败可以单独重试，不需要重新采集已经成功的页面。
- 报告清楚记录成功页数、失败页数、实际样本量和数据来源。

### 完成记录（2026-09-01）

- 搜索成功条件改为必须解析到有效 ASIN；HTTP 200 但零商品会自动进入备用通道。
- 已实现多请求标识、有限重试、退避、Jina Reader 备用读取、单页重试和部分样本显式授权。
- 真实端到端验收中第 2 页首次返回 HTTP 503，界面显示原因；点击“重试本页”后备用通道成功返回 48 款，三页完整后才开放分析。

## ISSUE-003：AI 分析过程过快且进度不代表真实任务

**状态：已完成**  
**优先级：最高**

### 现象

- 点击“AI 分析”后，七个分析阶段在约两秒内全部完成。
- 用户无法确认系统是否真正执行了数据清洗、特征提取、交叉分析和方案生成。
- 与视频中持续一段时间、逐项完成的分析过程不一致。

### 当前原因判断

1. 当前分析接口只执行本地确定性规则统计，通常在几十毫秒内完成。
2. 前端使用固定约 `280ms` 的计时器依次点亮七个阶段。
3. 七个阶段并未对应七个独立的后端处理任务，进度属于演示动画。
4. 当前没有调用大模型，也没有在分析阶段继续补充详情字段或执行语义级特征归纳。

### 处理方向

- 将分析改为真实的后端任务流水线，而不是人为增加固定等待时间。
- 拆分并实际执行：数据质量检查、清洗去重、字段覆盖率统计、价格与需求分析、设计特征归一化、锚点交叉对比、市场机会归纳、改款方案与依据生成。

## ISSUE-006：第一页收藏商品与前三页竞品的统计口径不够清楚

**状态：DEMO 已完成**  
**优先级：高**

### 运营反馈

- “收藏商品”展示的 48 款是否就是该关键词第一页的 48 款？
- “竞品搜索”再次抓取前三页，页与页之间是否会有重复商品？

### 事实确认

1. 收藏商品阶段只读取当前关键词的第 1 页，截图中的 48 款就是该页本次实际解析到的商品数。
2. 竞品搜索阶段分别读取第 1、2、3 页。Amazon 的广告位、排序波动和翻页机制可能让同一个 ASIN 跨页重复。
3. 当前系统在进入分析前会把三页商品合并，并按 ASIN 去重，所以重复商品不会重复进入核心分析。
4. 页面上的“每页 48 款”是各页原始数量；“去重商品数”才是分析实际使用的市场样本量。

### DEMO 必做

- 收藏页将文案改为“Amazon 搜索第 1 页，本页读取 N 款”。
- 竞品页同时展示：三页原始条数、重复 ASIN 数、去重后有效商品数。
- 报告头明确写“Amazon 前 N 个成功页面，共采集 X 条，按 ASIN 去重后 Y 款”。
- 当分页返回大量重复商品或疑似返回同一页时，标记分页异常并自动重试，不直接进入分析。

### 核心需求文档口径

- `rawResultCount`：每页解析到的原始商品条数。
- `duplicateAsinCount`：跨页重复 ASIN 数。
- `uniqueProductCount`：按 ASIN 去重后的实际分析商品数。
- 每个报告指标必须说明使用原始结果、去重商品还是变体 SKU 作为统计对象。

### 验收标准

- 用户无需询问即可分清第一页样本、前三页原始样本和去重分析样本。
- 相同 ASIN 不会重复影响价格、需求、颜色和设计特征统计。
- 分页异常与正常跨页重复能够被系统分别识别和说明。

## ISSUE-007：颜色统计误判、颜色口径与新品信号展示

**状态：核心误判已修复，颜色完整列表入口待补**  
**优先级：最高**

### 运营反馈

- 男士 Polo 报告显示“红色 69 个有效信号领先”，但商品明细中几乎看不到红色，怀疑颜色统计取值有误。
- “新品突破信号”只提示未取得上架日期，没有形成可用结论。
- 明细表显示“13 个、22 个颜色”，但页面只看见两个颜色名称，容易误解。

### 事实确认

1. 颜色统计确有误判：红色规则 `/red|burgundy/i` 会把 `Textured`、`Collared` 中的 `red` 当成红色。
2. 抽查当前 48 款 Polo 搜索结果，旧规则错误命中 20 款；按完整颜色单词识别后为 0 款。
3. 颜色统计把锚点和竞品合并时尚未再次按 ASIN 去重，可能造成少量重复计数。
4. 明细表颜色来自 Amazon Listing 的颜色变体节点和页面嵌入状态，不使用上述标题误判规则，属于真实公开字段。
5. 明细表当前只展示颜色总数和前两个名称，因此“22 个颜色”不等于只取得两个颜色。
6. 未取得上架日期时系统没有伪造数据，但继续展示“新品突破信号”业务价值较低。

### DEMO 必做

- 英文颜色使用完整单词和规范化后的颜色词识别，不能命中其他单词的局部字符。
- 颜色统计前对锚点与竞品按 ASIN 统一去重。
- 报告缓存增加分析版本；规则升级后不恢复旧的错误报告。
- 明细表颜色提供完整列表入口，并标明来源是 Listing 变体还是标题补充信号。
- 没有可靠上架日期时隐藏“新品突破信号”，动态替换为有数据证据的结论。

### 核心需求文档口径

- `listingVariantColors`：从 Amazon Listing 变体结构取得的颜色名称，可信级别高。
- `titleColorSignals`：仅从标题识别的颜色补充信号，可信级别中，不等同于 SKU 数。
- `colorProductCount`：包含某颜色的去重商品数。
- `colorVariantCount`：Listing 公开的颜色变体数。
- 颜色图表必须展示统计对象、覆盖商品数、来源和置信度。
- 新品分析只有在上架日期覆盖率达到产品设定阈值时才出现。

### 验收标准

- `Textured`、`Collared` 不再命中红色，真实 `Red`、`Burgundy` 仍能识别。
- 同一 ASIN 不会在颜色统计中重复计数。
- 用户能够查看颜色总数对应的完整颜色名称和来源。
- 数据不足时不再用“缺少上架日期”占据机会结论位置。

## ISSUE-008：设计特征过少且 67% 完整度容易误导

**状态：DEMO 规则已扩充，品类 Schema 与证据追溯待产品化**  
**优先级：最高**

### 运营反馈

- 裤装商品已经提取成功，但“设计特征”一列多数只有“褶裥”，信息明显偏少。
- 页面同时显示“67% / 完整提取”，容易让人误以为商品设计属性已提取完整。

### 事实确认

1. 当前设计特征使用有限的关键词规则，主要覆盖衬衫和上衣，裤装、Polo、T 恤等类目的属性词典不足。
2. 当前完整度按品牌、Bullet、颜色、BSR、上架日期、是否命中任意设计属性等六组字段计算；只命中一个设计标签也可能达到 67%。
3. 因此“请求与基础字段提取完成”基本属实，但“设计特征已经完整”并不成立。

### DEMO 必做

- 按品类建立设计属性 Schema，不再让所有服装共用一套上衣规则。
- 裤装至少覆盖：版型、裤腿、腰高、褶裥、门襟、口袋、面料/纹理、长度、弹力和使用场景。
- Polo/T 恤至少覆盖：领型、门襟、袖长、版型、面料、纹理、下摆、功能和使用场景。
- 将状态拆为“基础字段完整度”和“设计维度覆盖度”；设计维度不足时显示“设计特征部分提取”。
- 每个设计标签保留证据文本、字段来源和置信度，支持人工核验。
- 确定性规则负责标准字段；复杂语义和同义表达由可配置的大模型补充，但不能脱离 Listing 证据生成。

### 核心需求文档口径

- `fieldCompleteness`：价格、评分、评论、颜色、BSR 等基础字段覆盖率。
- `designCoverage`：目标品类设计维度中已取得的维度比例。
- `designAttributes[]`：标准属性名、标准值、原始证据、来源、置信度和提取方式。
- 不同类目使用不同属性模板，并允许版本化扩展。

### 验收标准

- 裤装样本不再只有“褶裥”单一标签，主要设计维度能够独立展示。
- 一个设计标签不能让商品显示为“设计特征完整”。
- 用户可以追溯每个属性来自标题、Bullet、详情表、变体数据还是语义分析。
- 报告中的设计统计只使用达到最低置信度的标准化属性。

## ISSUE-009：第一版原型增加轻量 MCP 真实数据验证

**状态：DEMO 已实现，待运营验收**  
**优先级：最高**

### 运营观点

- 希望补充关键词搜索量、竞争度、关键词反查和更完整的市场趋势，用于提高选品结论可信度。
- 设计共性应先转换成自然英文搜索词，再结合搜索量、竞争程度和头部集中度验证空白机会。
- 第一版不应依赖运营反复导出 SIF/卖家精灵文件，应优先尝试有免费额度的 MCP 轻量直连。
- 当前交付物是公司内部使用的可操作原型。当前阶段先梳理需求、问题和实现方案；确认后直接实现到 DEMO 供运营验收；运营确认整体方向后，再基于已验证页面补充逐页流程和核心需求文档，交由技术团队排期正式开发。

### 2026-09-03 数据源研究结论

1. 西柚洞察 MCP 提供周搜索量、ABA 排名、竞争难度、点击转化率、自然位滚动率、CPC 和头部 ASIN 份额；Free 套餐每月 20,000 Credit、每周 7,000 Credit，`get_keyword_info` 每查询 10 个关键词消耗 1 Credit，并明确允许购买方公司内部使用。
2. SIF MCP 的关键词历史、词根需求、竞争格局和机会筛选能力与运营流程高度匹配；公开页面称注册用户最高可领取 20,000 点，另有付费套餐。免费额度的具体领取条件和有效期需在账号控制台确认。
3. 卖家精灵 MCP 工具最完整，包含关键词、市场、评论和 Keepa 数据，但其公开密钥规范明确 MCP 仅限个人使用，不能集成企业内部系统；系统集成需改用卖家精灵 API，因此不进入本轮原型。
4. `amazon-sorftime-research-MCP-skill` GitHub 项目不是独立数据源，而是 Sorftime、SIF、西柚、卖家精灵的技能、脚本和报告集合。可复用其工具编排、字段说明和报告检查方法，但其中存在模拟数据、特定商品硬编码、经验阈值及疑似已泄漏凭证，禁止直接作为运行数据或复制公开密钥。

### 当前决策

1. 原型第一步优先接入西柚洞察 `get_keyword_info`，每次批量验证 3-8 个英文候选词，跑通“设计特征 -> 搜索词 -> 真实需求/竞争 -> 改款依据”。
2. SIF 保留为第二验证源，不在默认流程同时调用；待西柚链路稳定后，可对前 1-2 个候选机会词执行人工触发的深度验证。
3. GitHub 项目作为分析方法参考，不作为运行时依赖。允许借鉴其工具顺序、字段映射、证据链和报告模板，不引入其模拟数据、样例结论、公开凭证或整套 Python 运行环境。
4. 第一版不做多数据源融合、复杂评分、全属性笛卡尔组合、数据库任务队列或自动成功率预测。
5. Amazon 页面代理信号继续保留，但必须与 MCP 搜索量、关键词竞争度分开命名、存储和展示。
6. “使用场景”只有在 Listing 中存在明确证据时才能参与候选词生成，不允许加入默认旅行、度假等场景词。

### 原型本轮最小范围

- 根据基础关键词、性别/人群和已提取设计属性生成 3-8 个可编辑英文候选词。
- 每个候选词必须显示由哪些设计属性生成，用户可删除、修改或取消验证。
- 后端固定调用一个已知 MCP 工具，不让大模型自主选择多个工具或重复消耗额度。
- 报告增加关键词证据表和需求/竞争四象限；所有数值保留来源、指标周期和采集时间。
- 改款方案必须引用候选词及 MCP 指标；没有有效关键词数据时只展示原有 Amazon 公开证据，并明确本轮未完成关键词验证。
- MCP 密钥只保存在服务端环境变量；当前 cpolar 公网演示在启用 MCP 前必须增加最小访问控制和接口限流，防止外部访问和额度耗尽。

### 核心需求文档口径

- 原型只保留一个轻量数据适配层，不建设完整多 Provider 框架；输出仍需统一记录字段值、来源、指标周期、采集时间和授权范围，方便正式系统替换数据源。
- 商业数据源评估必须包含接口合法性、套餐费用、调用额度、更新频率、缓存许可和失败降级方式。
- 将 `searchVolume`、`keywordCompetition`、`salesEstimate` 与 Amazon 页面代理信号分开存储，禁止用评论量冒充搜索量或销量。
- MCP 是数据调用协议，不等于大模型。原型后端直接调用确定的 MCP 工具；大模型只负责术语校验、证据归纳和改款解释，不能改写原始数值。
- 完整调整范围、实施顺序和验收口径见 [`PROTOTYPE_REQUIREMENTS_PLAN.md`](PROTOTYPE_REQUIREMENTS_PLAN.md)。

6. 分类按实际改动解释，风险按证据缺口/工艺问题解释；数据不足时不强行评级。价格仅作样本参考，待核成本，取消序号驱动加价。

### 验收要点

- 运营能从方案读出“哪款商品、保留哪些、具体改哪里、依据是什么、还缺什么验证”。
